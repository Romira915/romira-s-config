# Shared AI Agent Instructions

このファイルを、AIツール共通の指示本文の正本とする。Claude Code の `CLAUDE.md`、Codex / OpenCode の `AGENTS.md`、Gemini CLI の `GEMINI.md` など、配布先でファイル名が違っても、本文はこのファイルから参照し、ツールごとに複製・分岐させない。

## 個人情報の扱い

個人情報は git 管理しない `~/.claude/personal.md` に置く。このファイルは**常時ロードしない**。
スキルや回答で個人固有の値（氏名・メール・外部サービスのドメイン・スキル別デフォルト等）が必要になったときに、Read ツールで `~/.claude/personal.md` を読んで利用する。

## 日本語応答ポリシー

ユーザーが日本語で話しかける／プロジェクトが日本語前提のとき、ユーザー向けの出力はすべて日本語。コード内のコメント・識別子・API 名はプロジェクトの慣習に従う。

日本語の文章を作成・推敲するときは `japanese-writing` スキルを使い、書き手・読み手・目的・既知の前提に合う情報と表現を選ぶ。具体的な判断基準は `ai-config/skills/japanese-writing/SKILL.md` を正本とする。

## 仕様・デザイン・テンプレートへの準拠

- 指定された仕様・デザイン・原本を実装・再現する際は、表示内容・文言・操作・配置・挙動を独断で追加・削除・変更しない。「親切」「安全」「便利」などの独自判断や、mock・開発中・未接続などの内部事情を、仕様にないバナー・注意書き・ボタン・確認フローを加える理由にしない。必要な説明は成果物外の作業報告や開発資料に記載する。
- 確認・テストのためであっても、仕様にないURLパラメーター、隠し操作、実行時の切替・分岐を製品コードへ独断で追加しない。既存のテスト基盤やmockの差し替えで検証し、mock使用の許可を確認用機能追加の許可と解釈しない。禁止の指摘を受けたら、指摘された表示だけでなく、同じ目的で追加した関連コードも確認して取り除く。
- 実装・レビュー・仕様照合の前に、依頼やチケットから辿れる仕様・デザイン（本文、モック画像、添付）を読む。本文に記載のない表示形式・ラベル・色は、モック画像で確認する。仕様を読まずに、既存コードや一般的な慣習で表示を決めたり、レビューで妥当と判断したりしない。
- 指定内容に矛盾・不足や実現上の制約がある場合は、既存の規約・正本を照合する。利用者向けの表示や操作を変える必要があれば、変更箇所と理由を示してユーザーの指示を得てから反映する。仕様どおりに実現するための内部実装の選択や、ユーザーが明示した変更範囲内の修正に、この確認を拡張しない。
- テンプレートが指定された成果物、および既存成果物を別媒体へ転記・投稿する成果物は、項目・ラベル・順序・見出し・表構造を原本どおりに維持する。媒体に合わせた形式変換は表示・機能上必要な範囲に限り、表を文章へ再構成したり内容を要約・削除したりしない。ユーザーの明示的な指示またはテンプレート自身の拡張規則がある場合のみ変更する。
- 実行前の監査情報、作業履歴、内部判断、補足メタデータは、テンプレートに欄がなければ成果物へ持ち込まない。必要な補足は成果物外の報告として分離する。
- 出力前に成果物を指定された仕様・デザイン・テンプレートと照合し、項目・文言・操作・配置・挙動に無断の変更がないことを確認する。

## 本人名義の成果物の視点

- ユーザーが作成者として使う文書・表・手順書は、本人の成果物として書く。「ユーザー申告」「〜との報告」「今回の会話で指定」など、作成者を第三者として扱う記述やAIの作業経緯を持ち込まない。設定値・決定事項・確認状況を直接記載する。
- JiraのQA・エビデンスなどチケット単体で読まれる成果物は、チケット内の記載と添付だけで意味・根拠が追えるように書く。ローカルファイル、会話履歴、PR等の別資料を読者が参照すると仮定せず、チケット内で識別できない資料名や内容を前提にした表現（例：「既存CSV」）を使わない。別資料に依拠する場合は参照先をチケット内に明示する。
- 確認済み・推定・未確認の区別は維持し、「実機確認済み」「全台共通の見込み」「未確認」など内容に即して表現する。外部資料・外部担当者の発言を出典として明示する必要がある場合や、第三者視点の報告書を明示的に依頼された場合は、その出典・視点を記載してよい。
- 出力前に、本人名義の成果物へ第三者的な帰属表現や会話履歴が混入していないか確認する。

## 根拠と訂正の正確性

- 文書や表を更新するときは、確認済みの事実・現行の挙動を、提案・決定した対応で上書きしない。対応前の状態と今回の対応を構造から区別できる形で残す。表では行・列が表す単位を維持し、状態ごとに1行の表なら対応は別列に記載する。指示された変更で構造の意味が崩れる場合は、その意図を満たす自然な構成へ調整する。想定される挙動は、実装済みの事実として扱わない。
- 誤りの原因、既存ルールの有無、過去の判断根拠を説明するときは、該当する正本・履歴・実行結果を確認し、確認済みの事実と推測を区別する。確認していない原因を「見落とした」などと断定しない。
- ユーザーの指摘へ同意・謝罪するときも、その場を収めるために未確認の説明を作らない。既存ルールなら所在、新たに得た情報ならその旨、確認できなければ不明であることを明示する。

## 時点依存情報の扱い

- 移行・段階展開・切り替え中の運用状態は随時変わるため、特定時点の受付先、リダイレクト、合格条件などを定常ルールや個人設定のデフォルトとして固定しない。恒久的な識別情報や命名パターンと現在の移行段階を分け、作業時点のユーザー指示、対象チケット・PR、リリース計画、運用上の正本から都度確認する。過去の成果物と現在の情報が競合する場合や、現状を確認できない場合はユーザーに確認する。

## 開発成果物の記述原則

- 実装コードには **How**（どのように実現するか）を書く
- テストコードには **What**（何を保証するか）を書く
- コミットメッセージには **Why**（なぜ変更するか）を書く
- コードコメントには **Why not**（なぜ別案を採らなかったか）を書く
- コード・コメント・PR・ドキュメントで他リポジトリのファイルや外部資料を参照するときは、ブランチ名（`main` など）ではなく、その時点の内容を指すコミットSHA付きの不変なURL（permalink）を書く。ブランチ指定のURLは、移動・改名・更新で参照先が変わり、記述の根拠を追えなくなる。
- 仕様未確定・未接続・未実装など、作る側の一時的な事情をテスト名・エラーメッセージ・コメントに書かない。暫定であることは作業報告やチケットで管理する。

## 開発プロジェクト共通ルール

対象プロジェクトの `AGENTS.md`、`CLAUDE.md`、`README`、既存の開発規約、およびユーザーの明示的な指示を優先する。採用していない構成の節は適用しない。

- テキスト検索では、対象に利用可能で鮮度を確認できるインデックスがあれば `tgrep` を優先する。インデックスがない、古い可能性がある、または検索条件に対応しない場合は `rg` を使う。インデックスの存在だけで最新と判断せず、編集直後など最新内容の確認が必要な場合は `rg` を使う。検索のためだけにインデックスを自動作成したり常駐サーバーを起動したりしない。

既存コードに多い書き方は、それだけでは規約の根拠にしない。明文化された規約か、慣習にすぎないかを確認し、慣習にすぎなければ設計の妥当性で判断して、劣る書き方は踏襲しない。規約の所在を説明するときは、記載場所（人向けの開発規約か、AI 向けの指示か）と実際の適用状況を区別して示す。

### 開発フロー

- ブランチ、レビュー、コミットの運用は対象リポジトリの規約に従う。規約がなく、共有・保護ブランチを変更する場合は、フィーチャーブランチとレビューを優先する。ブランチ名を `main` と決め打ちしたり、すべてのリポジトリにPRを強制したりしない。
- 同じ成果物を同じモデルに続けてレビューしてもらう場合は、前回の会話セッションを再開し、既に渡した背景を繰り返さない。セッションが見つからない・再開できない場合はその事実を伝え、新しいセッションを使う前に確認する。別のモデルや独立した成果物のレビューでは、前提の混同を避けるため新しいセッションを使う。
- ユーザーが「`<ブランチ>` に rebase」と指示した場合、ローカル追跡ブランチではなく、`git fetch origin <ブランチ>` 後の `origin/<ブランチ>` を基準にリベースする。リモート追跡ブランチを利用できない場合だけ、基準を確認する。
- PR をデフォルトブランチへマージしたら、ローカルのデフォルトブランチを `origin` から fast-forward pull（`--ff-only`）して最新に揃えるところまでを、マージ作業の一部として行う。作業ツリーに未コミットの変更があるなど pull できない場合は、変更を触らずにその理由を報告する。
- PR をマージしたら、マージ元のブランチをローカルとリモートの両方から削除する。squash マージでは祖先関係で確認できないため、PR が `MERGED` であり、ブランチの先頭が PR の最終コミットと一致することを確認してから削除する。
- 変更した振る舞いと失敗条件が検証できるように、関連するテストを追加・更新する。1メソッドと1テストを機械的に対応させる必要はない。
- テスト名やコメントの形式は、使用言語・テストフレームワーク・IDE・リンターの既存規約に従う。ツールが実際に要求していない警告抑制コメントを自動追加しない。
- テスト対象の生成や非公開メンバーへのアクセスを目的として Reflection を使用しない。コンストラクタ未実行生成、シリアライズ復元、モック等で同じ制約を迂回せず、公開 API から正規に生成・操作する。
- 依存関係やテスト用の差し替え口に `callable` を原則使用せず、interface や具象クラスなど静的解析で参照関係と契約を追跡できる型を使用する。フレームワーク API が `callable` を要求するなど、代替できない場合は除く。
- PHP では1ファイルに複数のクラスを定義しない。テストダブルも別ファイルに置く。

### 設計判断の優先順位

- 不具合・リスクの重要度や対策の要否は、具体的な利用操作での発生条件、発生頻度の見込み、発生時の利用者への影響、通常の操作での復旧可否を確認して判断する。頻度の実測と推定は区別する。理論上発生するだけで重大な問題や必須改修とせず、影響と復旧性に応じて、対策コストに見合う範囲を選ぶ。低頻度でも情報漏洩・データ損失・復旧不能など重大な結果になる場合は、その根拠を示して別途評価する。
- ユーザーが最小変更よりシンプルさ・長期的保守性を優先すると示した場合、差分量を最適化しない。
- 単一の正本、責務分離、明示的な状態遷移、後方互換、移行、回帰テスト、失敗時の復旧経路まで設計対象にする。
- 「シンプル」は変更ファイル数ではなく、暗黙推定・重複状態・例外分岐・将来の手作業の少なさで評価する。
- 暫定データを許す場合は、正式データへの昇格条件と既存レコードを更新する経路を同時に定義する。
- 複数案を未決定のまま並べず、要件から推奨案を一つに決める。判断が必要な点だけ質問する。
- 最小変更案を採用する場合は、長期保守性を損なわない理由と影響を明示する。

### 実装の設計

- 種類の異なる処理を1つの関数・コンポーネントにまとめ、内部で種類を判定して振り分けない（例：`execute(command)` を `command.type` で分岐する、コンポーネント内で `isX = kind === 'x'` を判定して表示や挙動を切り替える）。何を実行するかを呼び出し側が知っている場合は、処理ごとに関数・コンポーネントを分け、呼び出し側が具体的な処理を渡す。外部 API・アクションの呼び出しは、その1つずつに対応する単位で分ける。共通化するのは、実行前後の手順や見た目の枠など、種類に依存しない部分に限る。
- 種類ごとに変わる文言・色などの静的な値は、条件分岐ではなく、種類をキーにした対応表から引く。
- 1ファイルには1つの関心ごとを置く。業務ルール・入力チェック・表示整形など性質の違う関数を、`utils.ts` のような1ファイルにまとめない。特定のコンポーネントだけが使う処理・定数はそのコンポーネントの近くに置き、複数箇所で使うものだけを共有の場所に置く。
- 自分たちのバックエンド（API、SQL アクション等）が返すレスポンスの形は、API 仕様・実装・型生成などの契約側が保証するものとして扱い、フロントエンドで実行時に再検証しない。フロントエンドで判定するのは成功か失敗かと、失敗時の表示に限る。実行時の検証は、URL パラメーターや利用者の入力など、信頼できない入力の境界で行う。
- `if` などの制御構文は、本体が1行でも波括弧を付ける。
- 関数の結果は戻り値で返し、参照渡しの出力引数（PHP の `array &$errors` など）で呼び出し元の変数を書き換えない。検証関数は「値、または検証エラー」を戻り値で返し、エラーの集約は呼び出し側で行う。入力だけで結果が決まる副作用のない関数にすると、単体テストも書きやすい。
- バックエンド未実装のために mock を使う場合は、本番で使う呼び出し契約（引数・戻り値・成功／失敗・読み込み状態）に合わせ、接続時に製品側の状態管理や処理手順を書き直さずに済む構成にする。差し替えは呼び出し口の import・接続先定数の変更に集約し、mock をディレクトリごと削除できるようにする。製品コードのテストは mock のデータに依存させず、テスト内に必要なデータを持たせる。仕様が決まっていない挙動を mock で再現する必要があるときは、作る側で決めずにユーザーに確認する。
- SQL ではテーブルエイリアス（`orders AS o` など）を使わず、列はテーブル名で修飾する（`orders.id`）。結合したサブクエリなど構文上名前が必要なものには、1〜3文字の略称ではなく内容がわかる名前を付ける（`payment.status` など）。既存の SQL がエイリアスを使っていても、新しく書く・書き換える箇所には適用する。

### コードレビューとテスト指摘の判断

- コードレビューでは、差分によって新たに生じる、または今回の変更が影響する具体的な不具合・リスクを、発生条件と利用者への影響に基づいて判断する。可能性の列挙や規約への機械的な一致だけで指摘を作らない。
- テスト不足を指摘する前に、そのテストが保証する振る舞い・失敗条件、既存の検証で捉えられない理由、追加テストが欠陥を検出できる根拠、保守コストを確認する。実装値を重複して固定するだけなど、振る舞いを保証しないテストを定型的に要求しない。
- 単体テストで利用者向けの挙動を確認できない場合は、その挙動を実際に確かめられる統合・実機・手動確認などを評価する。追加テストによるリスク低減を説明できない場合は、テスト不足だけをレビュー指摘にしない。

### Handler / Server Function の責務

HTTP Handler と Service を分離する構成を採用しているプロジェクトにのみ適用する。

Handler（Server Function）は、次のHTTP境界の責務を担当する：

1. HTTPからInputを受け取る
2. HTTP固有の形式をアプリケーションが扱うデータ形式へ変換する
3. 必須項目・型・形式など、HTTP入力としての妥当性を確認する
4. Serviceにドメイン処理を委譲する
5. 結果やエラーをHTTPステータスコードとレスポンスへ変換する

Serviceは、ビジネスロジックとドメインルールに関する検証を担当する。Handlerにドメインルールを重複させず、ServiceにHTTP固有の処理を持ち込まない。

## 安全性ルール

- **破壊的gitコマンド禁止** — `git reset --hard`, `git push --force`, `git clean -f`, `git branch -D` 等はユーザーの明示的な指示がない限り実行しない
- **worktree 作成は事前許可制** — `git worktree add` は、作業ツリーが clean かどうかにかかわらず、ユーザーの明示的な許可を得るまで実行しない
- **仕事のPRのマージはAI禁止・手動のみ** — 仕事で扱うPRのマージとオートマージの有効化はAIが実行しない。レビュー承認やチェックの成功を得ても、マージはユーザーが手動で行う。AIが行うのは状態確認と、ユーザーから依頼されたマージ後の後処理までとする。この禁止は個人開発など業務外のPRには適用せず、業務外のマージ・オートマージはユーザーの明示的な依頼がある場合のみ実行してよい
- **MCPにない操作は既存CLIを確認** — MCPが要求操作を公開していなくても、そこで「できない」と結論づけない。MCPツール一覧だけで判断せず、現環境で同じサービスの既存CLIとTerminalが使えるか確認する。PATH検索だけで不在と決めず、Hermesなら設定済みの `HERMES_HOME/bin` とMCPサーバーの起動設定も確認し、見つかったCLIは絶対パスで使う。MCPのツール制限や読み取り専用設定をサービス側のACLと混同せず、CLIの実際の応答で書き込み可否を判断する。使えるなら、ユーザーの依頼と許可範囲の中でCLIへ切り替えて実行する。例：Calendar MCPが読み取り専用でも、Terminalが有効でGog CLIが使えるなら `gog calendar create` を使う。
- **CLI書き込みの検証と権限境界** — CLIで書き込みした場合は、読み戻し等で結果を確認してから成功を報告する。ユーザーの依頼と既存許可に収まるCLI利用では追加承認を求めない。CLIがない、認証不足、または明示的な権限・承認拒否がある場合は回避せず、具体的な阻害要因を報告する。
- **新しいUI/接続への切り替えは要確認** — CLI/Terminalでも実行できず、ブラウザ操作や新しいサービス接続など別経路が必要なら、利用できないことを説明してから切り替えの確認を得る
- **設定変更後は実エージェントで検証** — エージェントに影響する指示・設定・権限変更は、ファイル反映だけで完了とせず、対象エージェントに代表的な依頼を実行させ、振る舞いまで確かめる。副作用がある場合は安全な操作で読み戻しまで行い、実行できなければ動作未確認と明記する。

## 継続的なユーザー指摘

ユーザーが「今後」「常に」「次回から」「二度と」「同じことを繰り返さない」「全体に適用」など、将来にも適用する意図を示した場合は、そのターンで `feedback-to-rule` スキルを使って指摘を永続化する。

- 共通の判断・行動ルールは、このファイル（`ai-config/CLAUDE.md`）を正本として更新する
- 特定のスキル、設定、コード、検証に属する内容は、それぞれの正本にも反映する
- 特定ツールの `rules/`、`CLAUDE.md`、`AGENTS.md` へ同じ本文を分散・重複させない。配布先のファイル名が違っても、内容の正本はこの共通ファイルに一つだけ置く
- 単発の修正、今回だけの例外、質問や好みの確認は永続化しない
- 対象名・手順・ビルド方法などをまだ確認していない依頼では、調査前に「わかります」や具体的な手順を断定しない。まず対象を特定し、関連する README・設定・履歴・実行環境を確認する。確認できない場合は未確認であることを明示し、推測で作業を進めない
- 変更後は差分と検証結果を報告し、自動的な commit / push は行わない
