# バックエンドレビューの観点

レビューでも、実装前の設計でも使う。各項目は「何を確認するか」と「なぜか」を書く。該当しない項目は飛ばす。

## 1. データの前提（1対多・識別子・集約）

- **「1件のはず」という前提を、実装がどこで頼っているか。** 注文あたり決済1件、ユーザーあたり1行などの前提が、制約（一意制約・外部キー）で担保されているかを、テーブル定義で確認する。担保がないなら、前提が崩れたときの結果（欠損か、重複か、気づけるか）を評価する。
- **重複排除のキーは、業務上の識別子にする。** 親の ID（注文IDなど）で畳むと、別の取引が静かに1件に潰れて金額が欠ける。外部サービスが発行する取引IDなど、「同じ事象の二重記録は同じ値、別の事象は別の値」になる識別子を使う。
- **行を識別する値を、結果のDTOに持たせる。** 1親が複数行になり得る構造では、後続の処理が親のIDで集約しても、取引を区別できるようにする。
- **前提を DB 制約にできるか検討する。** 子テーブルが親の ID を持たない場合は、非正規化の列や部分一意インデックスが要る。既存データの確認と、スキーマ変更は別PRになる点も評価する。
- **重複記録のテストは、本当に重複を再現しているか。** 採番の都合で、別の識別子が入るデータを「重複」と呼んでいないか確認する。

## 2. 期間・時刻

- **期間は半開区間（開始 以上、終了の翌日0時 未満）に統一する。** 終了日を含む仕様でも、`終了日 23:59:59` との比較は秒未満が漏れる。境界のテストは、開始 `00:00:00`、終了日 `23:59:59`、翌日 `00:00:00` の3点を押さえる。
- **補い合う2つの抽出は、合わせて漏れがないか。** 「条件Aに合う」と「条件Bに合う」の和集合に、どちらにも入らない領域（例: 基準日より後の売上日）がないか、図に描いて確認する。隙間が起きる運用上の条件（時刻の出所の違い、前払いなど）があるかを、仕様に照らして判断する。
- **時刻の出所が違う値を比較していないか。** アプリ側の時刻と外部サービスの時刻を比べるなら、時計のずれ、タイムゾーン、境界付近の前後逆転を考える。実際に起きるかは、処理の順序と運用で判断し、根拠を残す。
- **除外条件は、実行する時刻に依存しないか。** 「現在までにキャンセルされた」ではなく「期間の終了時点までにキャンセルされた」のように、期間で固定する。実行日が違っても、同じ結果になる。
- **並びは決定的か。** 同値のときの第二ソートキー（ID など）を置く。1対多で1親が複数行になる場合は、その行の識別子も並びに含める。

## 3. SQL

- **外部結合の NULL を、DTO と出力が扱っているか。** 左外部結合で NULL になり得る列は、DTO を nullable にし、NULL の分岐をテストで一度は通す。出力側で空欄にしてよいかも仕様で確認する。
- **行ごとの副問い合わせ（LATERAL など）の対象件数。** 条件に下限がない（過去の全件が対象になる）と、件数に比例して遅くなる。期間内に該当がある行へ先に絞る（`EXISTS` など）と、プランが変わる場合がある。推測せず、合成データで実行計画を比べる。
- **インデックスの有無は、実行計画で確認する。** 絞り込み列にインデックスがないと、絞り込みの効果が出ない場合がある。追加はスキーマ変更として別の変更にする。
- **SQL の書き方（別名の扱い、文字列の書式など）は、リポジトリの規約に従う。** 規約を先に読む。規約がなければ設計の妥当性で判断する。
- **実行計画の取り方。** 本番相当の件数を模した合成データを、ロールバックされるトランザクション内に作り、`EXPLAIN (ANALYZE, BUFFERS)` を比べる。JIT のコンパイル時間が実行時間に含まれる点にも注意する。

## 4. 層の分担と構成

- **呼び出しの方向。** Handler（Action）は Service を呼び、Service が Repo を呼ぶ。Action が Repo を直接生成・呼び出ししていないか。業務ルールと Repo 呼び出しの組み立ては Service に置く。
- **1つのAPIに、1つの Action。** クエリパラメーターの違いで Action を分けず、1つの Action が、種類ごとの Service を受け取って選ぶ。種類ごとの静的な値（ファイル名の接頭辞など）は、種類をキーにした対応表から引く。エラー処理用の共有 Action は例外。
- **同じ処理の共通化は、将来の分岐を考えて決める。** 同じに見えても、将来どちらか片方だけ変わる可能性があるなら、重複を許す。同じものは1つにまとめる。
- **検証は副作用のない関数にする。** 参照渡しの出力引数を使わず、「値、または検証エラー」を戻り値で返し、エラーの集約は呼び出し側で行う。戻り値の型は、union ではなく、空配列が「正しい」を表すなど、分かりやすい形にする。
- **信頼できる境界でだけ検証する。** 自分たちのバックエンドが返す値は、契約が保証する。URL パラメーターや利用者の入力など、信頼できない入力で検証する。
- **配置。** DTO を文字列に組み立てるだけの純粋な処理は、同じ feature の前例（`Renderer/` など）に置き場所をそろえる。前例があるかは、同じ feature の既存ファイルで確認する。

## 5. ファイル・CSV 出力

- **列・列順・書式を、仕様の表と1つずつ照合する。** 日付書式、ヘッダー行、0件のときの出力、文字コードを含む。
- **文字コードで表せない文字の扱い。** 例外にして出力を止めると業務が止まる場合は、置換して出力し、利用者が手作業で直す運用にする。置換文字が実行環境の設定（`php.ini` など）に依存するなら、コメントに書く。設定を固定する関数は、同じリクエスト内の他の処理に影響するので、固定する前に副作用を評価する。
- **数式として評価される文字（`=` `+` `-` `@`、タブ、CR）で始まる文字列を無効化する。** 外部システム由来の値は、先頭の文字を保証できない。生成値（数値・日付）は対象外でよい。引用符の囲みと、`"` のエスケープの順序も確認する。
- **期間に上限がない出力は、全行をメモリに載せる。** 当面の件数で問題ないなら、記録だけ残し、直さなくてよい。

## 6. テスト

- **データの後始末。** 登録したデータの削除方法（トランザクションのロールバックを使うか、明示的に削除するか）は、リポジトリの規約に従う。規約が明示的に禁止しているなら、テストが登録した ID の範囲を、`setUp`（残りを消す）と `tearDown` で明示的に削除する。
- **失敗させる方法。** 呼び出し先を失敗させたいときは、例外を投げる差し替え（モック）を注入する。中断したトランザクションなど、副作用に頼らない。
- **期待値は、実装と同じ計算で作らない。** リテラルで固定する。変換結果（エンコードされたバイト列など）は、デコード後の内容と、そのバイトを選んだ理由をコメントに書く。
- **仕様が疑わしい挙動を、テストで固定しない。** 欠損につながるかもしれない挙動を期待値にすると、確認が済むまで、その挙動が「仕様」に見える。
- **名前は振る舞いを表す。** 実装の詳細や、一時的な事情（未接続・仕様未確定）は書かない。
- **テストの土台が古くないか。** ローカルの検証用スキーマが古いと、必須列が増えた後にも通る。CI は最新の基準ブランチで走るので、登録するデータの列が、最新のスキーマと合っているかを確認する。
- **各層の境界のテスト。** Repo は実DB、Service は Repo を通した結果、Action は Service の成功と失敗（500）というように、層ごとに保証することを分ける。

## 7. PR の分割と進め方

- **大きいPRは、層ごとに分ける。** Repo、Service、Action、入口（ルーティング）の順に、積み重ねて出す。各PRは、単独で読め、単独でテストが通る範囲にする。
- **積み重ねの PR の base と本文。** base が別ブランチのとき、本文にその旨を書く。下のPRがマージされて base が付け替わったら、本文を直す。
- **土台を直すと、上のPRも更新が必要。** コンストラクタやDTOの形を変えたら、上に積んだPRのテストも追随させる。履歴を書き換える場合は、強制 push が必要になるので、事前に確認する。
- **作る前に、最新の基準ブランチに rebase する。** 土台が古いと、無関係なテストが失敗して見える。失敗が自分の変更に関係するかは、失敗したテストの名前と原因で切り分ける。
- **仕様と実装の構成の食い違いは、実装前に気づく。** チケットが API の形（1つのAPI、種別パラメーター）を決めているなら、分割の判断より先に、それを確認する。
