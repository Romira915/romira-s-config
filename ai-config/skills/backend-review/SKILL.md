# バックエンドレビュー

PR または差分を、仕様・規約・データの前提に照らしてレビューし、根拠のある指摘だけを報告する。修正の適用、コミット、PRへのコメント投稿は、ユーザーが依頼したときだけ行う。実装前の設計チェックにも、同じ観点で使う。

## 引数

- `$ARGUMENTS` に PR 番号または URL、ブランチ名を指定する。
- 省略時は現在のブランチの差分（`git diff <base>...HEAD`）を対象にする。
- 「自分のPRの事前チェック」「実装前のチェック」と言われた場合は、手順3の観点を、書く前の設計の確認としても使う。

## 手順

### 1. 仕様と規約を読む（指摘を作る前に必ず）

- PR 本文・チケットから、設計資料・受け入れ条件へのリンクを辿り、本文を読む。**API の形（パス数・パラメータ・返却形式）、列・書式、対象範囲、除外範囲**を、実装と照合する。仕様が一つのAPIを前提にしているのに実装が分かれている、といった構成の食い違いも指摘対象にする。仕様を読めなかった場合は、その旨を報告に残し、一致と判断しない。
- リポジトリの `AGENTS.md`、`CLAUDE.md`、`CLAUDE.local.md`、README、開発規約を読む。ユーザー固有の指示は共有の指示より優先する。規約の根拠は、記載場所と実際の適用状況を区別する。既存コードに多いだけの書き方は規約の根拠にしない。
- 根拠がチェックインされていない個人用の指示だけの場合、PR の作成者はそれを読めない。PR への指摘は「規約違反」と書かず、設計上の理由と影響で書く。

### 2. 差分を取得する

- `gh pr view <番号> --json title,body,headRefName,baseRefName,files` と `gh pr diff <番号>` を使う。長い差分は一時ファイルに保存して読む。
- 差分が依存・影響する既存コード（呼び出し元、テーブル定義、既存の Service/Repo）は、その範囲だけ読む。
- PR が積み重ね（base が別ブランチ）の場合は、base と最新のデフォルトブランチの差を確認し、土台の古さが失敗の原因になっていないかも見る。

### 3. 差分をレビューする

観点は `references/backend-checklist.md` を読んで適用する。次の判断基準は常に守る。

- **差分で新たに生じる、または今回の変更が影響する具体的な不具合・リスク**を、発生条件と利用者・業務への影響で判断する。可能性の列挙や、規約への機械的な一致だけで指摘しない。
- 重要度は、具体的な操作での発生条件、発生頻度の見込み（実測と推定は区別する）、影響、復旧の可否で決める。理論上起きるだけの問題を必須とせず、対策コストに見合う範囲を選ぶ。情報漏洩・金額の欠損・データ損失・復旧不能は、低頻度でも根拠を示して別に評価する。
- 性能の指摘は、推測で重要度を決めず、**実行計画と実行時間**（本番相当の件数、またはそれを模した合成データ）で裏付ける。裏付けがないときは「推定」と明記する。
- 「起きない」とされる前提（1対多にならない、順序が逆転しない等）は、前提を確認する指摘にする。起きない根拠（仕様・運用）と、崩れたときの影響（欠損か、重複か、気づけるか）を並べて評価し、DB制約で担保できるか（実現方法と既存データへの影響を含む）も検討する。
- テスト不足は、そのテストが保証する振る舞い、既存の検証で捉えられない理由、追加テストが欠陥を検出できる根拠、保守コストを確認してから指摘する。

### 4. 検証する（できる範囲で、結果を区別して報告）

- 対象のテスト、静的解析、整形は、リポジトリの手順で実行する。ローカルの検証用データが古い場合は、最新の基準ブランチのスキーマで再確認する。実行したコマンドと結果を報告に書く。
- 実行計画の取得などローカルDBへの操作は、プロジェクトの手順で行い、書き込みを伴う場合は戻る形（ロールバックされるトランザクション内）にする。本番の直接操作はしない。
- 実行していない検証を「問題なし」と書かない。

### 5. 報告する

次の順で、日本語で報告する。

1. 結論（マージを止める問題の有無）
2. 指摘（重要度順）: 場所（`path:行`）、何が起きるか（発生条件と影響）、直し方
3. 仕様との一致の確認結果（食い違い・読めなかった資料）
4. 確認済み・推定・未確認の区別（実行したコマンド、測っていない性能、確認できていない前提）
5. 仕様の確認が必要な点は、コードの指摘と分け、誰に何を確認するかを書く

## レビューコメントへの対応判断（自分のPRが受けた指摘）

- 指摘の事実（引用された規約、存在するはずのファイル、挙動）を、自分で確認してから採否を決める。確認できない根拠は、その旨を添える。
- 採否は、「対応する／対応しない／仕様の確認が必要」に分け、対応しない理由と、残るリスクを書く。判断に迷う仕様は、実装で補完せず確認する。
- 自分の過去の説明が誤っていたと分かったら、そう訂正してから進める。
- GitHub への返信・コメント・PR本文の更新は、下書きを示し、ユーザーが明示的に承認してから行う。

## 注意

- 原因・既存ルールの有無・過去の判断根拠を説明するときは、正本・履歴・実行結果を確認し、推測と区別する。
- 質問に答えるだけの依頼では、コードを変更しない。修正を依頼されたら、その範囲だけ直し、テストと静的解析の結果を報告する。
- コミット・push・PR作成・強制push・rebase は、依頼があるときだけ行う。コミットメッセージは Why を書く。
- 継続的に適用したい指摘は、`feedback-to-rule` スキルでの永続化をユーザーに提案する。
