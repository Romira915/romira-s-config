# 日本語の文章を書く

読み手が、必要な内容を自然な日本語で理解し、求められた判断や行動につなげられる文章にする。情報を増やすことや短くすること自体を目的にしない。

## 書く前に判断すること

依頼、既存文書、会話、必要な資料から、次を把握する。これを毎回ユーザーへの質問や成果物内のチェックリストにしない。不明な点が文章の意味や結論を変える場合だけ確認する。

| 観点 | 判断する内容 |
|---|---|
| 誰が書くか | 著者と読み手の関係、権限、責任。本人の文書か、第三者の報告か |
| どういう目線か | 提案者、実施者、報告者、説明者など、どの立場から何を述べるか |
| 何を求められているか | 理解、判断、承認、実行、記録など、この文章の用途 |
| 何を書けばわかるか | 読み手が結論に至るために必要な事実、条件、理由、具体例 |
| 前提は何か | 読み手の知識、既存の運用、対象範囲、現状、決定済み事項 |
| 何を書くと余計か | 読み手にとって当然の説明、主題と無関係な補足、重複、不要な否定 |

## 情報を選ぶ

- 各文が、読み手の理解・判断・行動に何を加えるかを考える。役割のない説明は加えない。
- 発表では、画面の文字・図・画像ごとに、聞き手が何を受け取り、場面・気持ち・行動をどう想像しやすくなるかを確認する。情報が正確であること、根拠を収集したこと、文字が読めることだけを、画面に載せる理由にしない。出典の日時・資料名や確認用の詳細は、話の理解・判断に必要な場合、または提示義務がある場合に表示し、それ以外は参照先をノートや参考資料に残す。図も項目の羅列を装飾するだけにせず、聞き手が理解すべき関係や具体的な利用場面を示す。
- 経験や成長を伝える発表・振り返りでは、「何をし、そのとき何を感じ、どう考え、何を引き受けたか」が聞き手に伝わる情報を選ぶ。業務の分担・相談先・実施手順は、その経験や判断の意味を理解するために必要な範囲で述べる。分担の説明を整えることを、本人の行動や思いを伝えることの代わりにしない。
- 具体的な行動と感情・判断を結びつける際は、本人が振り返った事実に基づく。分担や手順を省くことで実際以上の権限・単独成果に見せたり、抽象的な決意だけにしたり、未確認の感情や行動変化を補ったりしない。
- 仕様に機能が存在することと、対象の設計で必要なことを区別する。適用条件や必要性を確認していない機能を、条件付きの補足や実装指示として勝手に追加しない。
- コード例・設定例から明らかな値や、読み手に自明な既存実装との一致を、本文で逐一言い直さない。説明を加えるのは、意味が曖昧な値、変更理由、判断に必要な制約がある場合に限る。
- 色・太字などの強調は、文書の目的に照らして判断条件・影響・変更点を見つけやすくするために選ぶ。ユーザーが確認・言及したことだけを理由に重要扱いせず、設定値を一律に強調しない。
- 既存の運用と今回の変更を区別する。「行う」「導入する」「実行する」などの表現で、すでに行われていることを新しい施策に見せない。「既存の」で今回必要な追加作業まで実施済みに見せない。
- 既存の前提は、今回の違いや制約を理解するために必要な範囲で書く。読み手が知っている通常の運用を、今回の決定事項として説明し直さない。初心者向けの説明、引き継ぎ、運用手順など、前提の明記が必要な用途では省かない。
- 関連事項を網羅するためだけに、採用していない案や「〜しない」という説明を追加しない。読み手が実際に誤解し得る点や重要な境界を示す場合に使う。
- 専門用語は、読み手が意味を理解できるかで説明量を決める。用語を別の専門用語へ置き換えるだけで説明を終えない。補足が主題を遮る場合は、媒体と既存形式に応じて注記・トグルなどを使う。
- 主題に必要な条件、失敗条件、意味のある例外は、短くするために削らない。テンプレートの項目・構造や、指定された事実を情報量の判断だけで省略しない。

## 文の役割と根拠を明確にする

- 事実、今回の方針、提案、未決定事項を、動詞と時制で読み分けられるようにする。未決定の内容を実施方針として書かない。
- 評価・依頼・提案・決定を表す言葉は、書き手と読み手の関係、判断権限、合意の段階に合わせて選ぶ。書き手を外部の評価者に変えたり、読み手に委ねている判断を決定済みに見せたりしない。特定の語を一律に禁止せず、その文書で誰が誰に何を述べるのかで判断する。
- 表では、行が状態・対象・事例のどれを表し、列がどの比較項目を表すかを確認してから追記する。状態ごとに1行の表では、対応前の挙動と今回の対応を別列に記載し、対応のために同じ状態の行を増やさない。同じセルに混在させたり、対応内容で元の挙動を置き換えたりしない。未実装の仕組みによる想定と現行実装の事実も区別する。
- リスクを書くときは、発生条件と具体的な不利益・影響を示す。「可能性がある」「検討が必要」だけで終えない。対策を書くなら、それが決定済みか提案かも明確にする。
- セキュリティ、障害、テストなどの節では、その節の目的に答える。既存設計の説明を繰り返して、何が懸念なのか、何を確認するのかを読者に推測させない。
- システムの挙動や運用を根拠に書く場合は、該当する実装・規約・仕様を確認する。処理の一部だけを見て、前後の処理や別経路を含む結論を断定しない。一般論から具体的な障害やリスクを作らない。
- 前提が不足する場合は、確認済みの範囲を述べるか、必要な確認を行う。推測を文書上の確定事項にしない。

## 日本語として整える

- 主語を明記すべき箇所と、省略しても自然に伝わる箇所を区別する。動作主体が切り替わる文、複数の解釈ができる文では主体を明示する。
- 条件と結果、原因と影響、目的と手段を対応させる。接続詞を足して論理の不足を埋めたように見せない。
- 「これ」「それ」「既存の処理」などは、読み手が参照先を特定できる場合に使う。会話や別資料を見ないと意味が通らない指示語は具体化する。
- 一つの文に異なる役割や主体を詰め込まない。関連する文をつなぎ、箇条書きは比較や手順など読みやすくなる場合に使う。
- 書き手の立場、用語、文体を既存文書に合わせる。本人名義の成果物へAIとの会話や第三者的な帰属表現を持ち込まない。

## 出力前の読み直し

会話を知らない想定読者として読み、次を確認して修正する。

- この文章で何がわかり、どの判断・行動につながるか。
- 発表では、聞き手が各表示から何を受け取り、どの場面・気持ち・行動を想像できるか。表示を見て読む負担が、その理解を助ける効果に見合っているか。
- 現状、今回の変更、未決定事項を取り違えないか。
- 「なぜここに当然のことを書いているのか」と感じる文がないか。
- 省略したことで条件・意味・責任が変わっていないか。
- リスクや対策の主体・条件・影響が伝わり、根拠を説明できるか。
- 日本語の流れが自然で、読者が足りない関係を補わなくても読めるか。
