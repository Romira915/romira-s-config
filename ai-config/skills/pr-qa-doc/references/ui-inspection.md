# UI確認による正式名称とケース粒度の決定

画面を伴う QA で、PR description やチケットだけでは正式名称またはケース間の関係を確定できない場合に読む。

## 正式名称

- コード上の識別子、内部処理名、開発者間の略称を画面名や操作名として使わない
- 画面見出し、ステップ名、ラベル、ボタン名は、実画面に表示された文字列をそのまま使う
- 実画面を確認できない場合は実装から表示名を推測せず、ユーザーに確認する
- ユーザーがブラウザ操作手段を指定した場合はその手段を使い、利用できなければ無断で切り替えない

## ケースの分割・統合

- コード上の分岐数だけでケース数を決めず、画面のコントロール種別、排他性、同時選択の制約、遷移先、観測可能な期待結果を確認する
- 排他的な操作、別の画面遷移、または異なる期待結果になる選択肢はケースを分ける
- 同じ操作フロー内で同時に選択でき、合格条件とエビデンスが共通する選択肢は 1 ケースへまとめる。ただし別のコード経路を個別に保証する必要があれば分ける
- 複数の条件軸がある場合は、各軸が期待結果へ影響する組み合わせだけを残す

## 状態変更と認証情報

正式名称やケース粒度は、まず一覧・詳細・確認画面など読み取り専用の場所で確認する。既存の下書きや編集ウィザードは、自動保存などで状態が変わり得るため調査目的だけで操作しない。

- 編集フローが必要なら状態変更の可能性を説明し、ユーザーの許可を得る
- 許可後も専用の破棄可能な QA データを優先し、操作前後の状態を比較する
- 調査中に登録・公開・送信などの確定操作を行わない
- 分離ブラウザコンテキストを使い、完了後に認証済みページを閉じる
- 認証情報はユーザー指定の手段または個人設定から取得し、コマンド出力、ツール応答、ログ、ファイル、QA 文書へ表示・保存しない
- 秘密値を安全にブラウザへ渡せない場合は、ユーザーへログイン操作を依頼する
