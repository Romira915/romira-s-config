# フロントエンドレビューの観点

プロジェクトの規約と食い違う場合は、プロジェクトの規約を優先する。

## 状態管理（React）

- 実行中・読み込み中・エラー・取得結果は、データ取得 hook が返す状態から導く。同じ内容を `useState` や `useEffect` で持ち直さない。
- `useRef` を二重実行の防止など、再描画に関わる状態の代わりに使わない。`useState` か、hook が返す `loading` を使う。使う場合は、再描画を待てない理由をコメントで残す。
- `useEffect` でのデータ取得・状態の同期は、まず不要でないか疑う。取得は取得用の hook、導出できる値は描画中に計算する。
- hook の引数に `undefined` を許して内部で分岐しない。値が確定している前提で受け取り、分岐は呼び出し側（上位コンポーネント）に置く。

## 設計

- 種類の異なる処理を1つの関数・コンポーネントにまとめ、内部で種類を判定して振り分けない。呼び出し側が知っているなら、処理ごとに分ける。共通化は、実行前後の手順や見た目の枠など、種類に依存しない部分に限る。
- 種類ごとに変わる文言・色などの静的な値は、条件分岐でなく、種類をキーにした対応表から引く。
- 1ファイルには1つの関心ごとを置く。業務ルール・入力チェック・表示整形を `utils.ts` のような1ファイルに混ぜない。特定のコンポーネントだけが使うものは、そのコンポーネントの近くに置く。
- 自分たちのバックエンドが返すレスポンスの形は、契約側が保証するものとして扱い、実行時に再検証しない。実行時の検証は、URL パラメーターや利用者の入力など、信頼できない入力の境界で行う。
- 本体が1行でも `if` に波括弧を付ける（lint で検出できない場合がある）。

## mock・未接続のバックエンド

- mock は、本番で使う呼び出し契約（引数・戻り値・成功／失敗・読み込み状態）に合わせ、接続時に製品側の状態管理や処理手順を書き直さずに済ませる。
- 差し替えは呼び出し口の import や接続先の定数に集約し、mock をディレクトリごと削除できるようにする。製品コードのテストは mock のデータに依存させない。
- 仕様が決まっていない挙動を mock で再現するときは、作る側で決めず、確認を求める。

## 日時・タイムゾーン

- タイムゾーンの有無で解釈が変わる値（ブラウザのタイムゾーンに依存する値）を受け取る関数は、想定する形式を確認する。契約で保証されないなら、タイムゾーンなしをエラーにする。
- 表示する時刻のタイムゾーンを明示して整形する。サーバーと画面のどちらで変換するかを、プロジェクトの規約に照らして確認する。
- 日付だけの文字列（`YYYY-MM-DD`）の比較は文字列比較で足りるが、時刻を含む比較・範囲の境界（終日を含むか）は、API 側の解釈を確認する。

## UI・アクセシビリティ

- 入力チェックのエラー表示は、仕様の文言・位置・タイミング（入力した時点か、送信時か）に合わせる。エラー中に操作を無効にする仕様は、ボタンの `disabled` まで確認する。
- フォーム部品は、ラベルと関連付ける（`aria-label` か `label`）。エラーメッセージは入力部品と関連付ける。
- 使用している UI ライブラリの既定の挙動（例: ボタンの枠線の色が文字色になる）を、見た目の仕様と照らす。
- 失敗時は利用者に分かる形で通知し、成功でも失敗でもない結果を無言で捨てない。

## テスト

- テストを提案する前に、プロジェクトのテスト方針・実行環境・依存の配布形態を確認する。外部プラットフォームを多数の mock で置き換える必要があり、実際の連携を保証できない場合は、純関数で保証する範囲とブラウザ・実機で確認する範囲を分ける。テスト専用の依存追加も、この方針と検証できる挙動に基づいて判断する。
- 変更した振る舞いと失敗条件が検証できるか。境界値（月初・月末・うるう年・タイムゾーンをまたぐ時刻）は、純粋関数のテストで確認できているか。
- テスト対象の生成や非公開メンバーへのアクセスに Reflection や型の迂回を使っていないか。
- テスト名・エラーメッセージ・コメントに、仕様未確定・未接続・未実装などの作る側の事情を書いていないか。
