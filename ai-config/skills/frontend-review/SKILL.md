# フロントエンドレビュー

PR または差分を、仕様・規約・過去の指摘に照らしてレビューし、根拠のある指摘だけを報告する。修正の適用、コミット、PRへのコメント投稿は、ユーザーが依頼したときだけ行う。

## 引数

- `$ARGUMENTS` に PR 番号または URL、ブランチ名を指定する。
- 省略時は現在のブランチの差分（`git diff <base>...HEAD`）を対象にする。
- 「自分のPRの事前チェック」と言われた場合は、手順4（再発確認）を必ず行う。

## 手順

### 1. 仕様と規約を読む（指摘を作る前に必ず）

- PR 本文から、チケット・設計資料・モック画像へのリンクを辿り、本文・添付を読む。本文にない表示形式・ラベル・色はモック画像で確認する。画像を読めなかった場合は、その旨を報告に残し、一致と判断しない。
- リポジトリの `AGENTS.md`、`CLAUDE.md`、`CLAUDE.local.md`、README、開発規約を読む。ユーザー固有の指示（`CLAUDE.local.md` など）は共有の指示より優先する。
- 規約の根拠を示すときは、記載場所（人向けの開発規約か、AI 向けの指示か）と実際の適用状況を区別する。既存コードに多いだけの書き方は規約の根拠にしない。
- 根拠が `CLAUDE.local.md` などチェックインされていない個人用の指示だけの場合、PR の作成者はその内容を読めない。PR への指摘は「規約違反」と書かず、設計上の理由と利用者への影響で書き、重要度もそれで決める。

### 2. 差分を取得する

- `gh pr view <番号> --json title,body,headRefName,baseRefName,files` と `gh pr diff <番号>` を使う。
- 差分が長い場合は一時ファイル（スクラッチパッド）に保存して読む。
- 差分が触れていない既存コードは、差分が依存・影響する範囲だけ読む。

### 3. 差分をレビューする

観点は `references/frontend-checklist.md` を読んで適用する。次の判断基準は常に守る。

- **差分で新たに生じる、または今回の変更が影響する具体的な不具合・リスク**を、発生条件と利用者への影響で判断する。可能性の列挙や、規約への機械的な一致だけで指摘しない。
- 重要度は、具体的な操作での発生条件、発生頻度の見込み（実測と推定は区別する）、利用者への影響、通常の操作での復旧可否で決める。理論上起きるだけの問題を必須とせず、対策コストに見合う範囲を選ぶ。情報漏洩・データ損失・復旧不能は、低頻度でも根拠を示して別に評価する。
- テスト不足は、そのテストが保証する振る舞い、既存の検証で捉えられない理由、追加テストが欠陥を検出できる根拠、保守コストを確認してから指摘する。実装値の重複を固定するだけのテストは要求しない。単体テストで確かめられない挙動は、統合・実機・手動確認を評価する。
- 仕様にない表示・操作・挙動の追加や変更は、親切・安全などの理由があっても指摘対象にする。

### 4. 過去の指摘との照合（再発確認）

今回の PR の作成者が直近にマージした PR で、人間のレビュアーから受けた指摘と同じことをしていないか確認する。自分の PR なら `--author @me`、他人の PR をレビューするときは作成者のログインを `--author` に指定する。

1. `gh pr list --author <作成者> --state merged --limit 10 --json number,title,mergedAt` で直近の PR を得る。
2. 各 PR について、`gh api repos/<owner>/<repo>/pulls/<番号>/comments`、`.../pulls/<番号>/reviews`、`.../issues/<番号>/comments` から、`user.type == "User"` のコメントだけを取り出す（bot の出力は量が多いため除外する）。
3. 指摘の内容を、今回の差分の該当箇所と突き合わせる。同じ種類の書き方があれば、元の PR 番号と指摘の要旨を添えて報告する。
4. 該当がないものも、一覧にして報告する（確認した範囲が分かるようにする）。

指摘が将来にも適用される規約なら、`feedback-to-rule` スキルでの永続化をユーザーに提案する。

### 5. 報告する

次の順で、日本語で報告する。

1. 結論（マージを止める問題の有無）
2. 指摘（重要度順）: 場所（`path:行`）、何が起きるか（発生条件と利用者への影響）、直し方
3. 仕様との一致の確認結果
4. 過去の指摘との照合結果
5. **引用の正確さ**: 指摘の場所は、diff 上の行ではなく PR ブランチのファイル上の行で示し、取得元（ブランチ名）を書く。ローカルのブランチと違うときは、リンクが別のファイルを指しうることを添える。修正案で新設を提案するコンポーネント・関数の名前には「新規」と明記し、既存のものと誤認させない。
6. **確認済み・推定・未確認の区別**: 実行したコマンド（lint・テスト・ビルド）、読めなかった資料（モック画像など）、接続先が未確定で見ていない契約を明記する。実行していない検証を「問題なし」と書かない。

## 注意

- 原因・既存ルールの有無・過去の判断根拠を説明するときは、正本・履歴・実行結果を確認し、推測と区別する。確認していないことを断定しない。
- 質問に答えるだけの依頼では、コードを変更しない。修正を依頼されたら、その範囲だけ直し、対象ディレクトリの lint・型チェックの結果を報告する。
- コミットは依頼があるときだけ行う。メッセージは Why（なぜ変更するか）を書く。
