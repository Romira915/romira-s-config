# メール配信 QA の証拠境界

メール送信、受信、またはメールヘッダーを合格条件に含める場合に読む。

## 宛先の記録

画面上で指定した送信対象と、受信ボックスで観測できた宛先を同一視しない。

- 画面の選択内容は、リスト名、ユーザー種別、選択件数など UI に表示された値として記録する
- 受信結果は、メール原文で観測した `To` / `Delivered-To` として記録する
- リスト展開や転送を含む場合は、UI 上の選択内容と最終受信アドレスをそれぞれ別の証拠で示す

## 送信対象ごとの証拠充足

期待結果に複数のリスト、ユーザー種別、または個別宛先を列挙した場合は、送信対象ごとに最終受信の証拠を対応付ける。

- 各送信対象について、最終受信アドレスと、それを確認できるメール原文の `To` / `Delivered-To` または配送ログを記録する
- 受信スレッド数やメッセージ数だけでは送信対象を識別できないため、宛先別の証拠として扱わない
- リストの展開先を確認する場合は、UI 上のリスト名・選択件数とは別に、展開後の最終受信アドレスを確認する
- 全件への配送が合格条件なら、配送ログ等で全件数を確認したうえで、送信対象ごとの代表的なメール原文も確認する。代表確認だけへ縮小する場合は、事前にユーザーと合意した範囲を明記する
- 期待結果に挙げた送信対象のうち1つでも証拠がなければ、そのテストケースは OK にせず未確認とする

QA Markdown を完成させる前に、次の対応表で空欄がないことを確認する。

| 送信対象 | UI 上の選択証拠 | 最終受信アドレス | 最終受信の証拠 |
|---|---|---|---|
| `<list-or-user-type>` | `<screen-or-log>` | `<address>` | `<raw-mail-or-delivery-log>` |

## 複数の受信箱を使う環境

送信先によって Gmail、MailCatcher、その他の受信箱へ分かれる構成では、1つの受信箱だけを検索して未着と判定しない。

- ユーザーが指定した受信箱をすべて確認し、送信対象と確認先の対応を記録する
- 同一件名の受信数を確認するときは、受信箱ごとの一意な最終受信アドレスを集計し、受信箱をまたいだ重複を除く
- 件数だけで合格にせず、リスト展開先・ユーザー種別・個別宛先を識別できる代表メールも開いて確認する
- 画面上のリスト件数は媒体レコード数である場合があるため、最終受信メールアドレス数とは分けて記載する

## 受信データが保持期間外の場合

受信箱から対象メールが消えている可能性がある場合は、未着と断定せず、対象リビジョンのデプロイを確認してから該当ケースを最初から再実行する。

- 再実行時も、比較対象となる既存ケースと同じタイトル・入力条件を使う
- タイトルへ「再テスト」「再々テスト」「retry」などの実行履歴を足さない
- 最終文書には有効な最新実行のリリースID・受信結果・証拠だけを残し、「追記」「再実行分」などの作業履歴として分離しない
- 古い配信結果や保持期間外の証拠は、現行ケースの合否根拠として再利用しない

## ヘッダーの観測境界

ヘッダーを合格条件にする前に、どの境界で存在すべきかを特定する。

- ヘッダーの付与・非付与が複数の送信対象へ共通して適用されることを合格条件にする場合は、送信対象の種別ごとに最終受信原文を確認する。別種別の代表1件だけで全種別を合格にしない
- 送信対象ごとのヘッダー確認画像は、該当ケースのエビデンス欄へすべて表示する。各画像の直前に、受信箱の画面名、送信対象の種別、最終受信アドレス、確認したヘッダーの状態を記載し、ファイル名や画像パスだけを証拠にしない
- 同じ画像が受信先とヘッダーの両方を十分に示す場合は重複する受信確認画像を省く。ただし1枚で識別できない場合は、受信先を示す画像と原文ヘッダー画像を組み合わせる

| 観測境界 | 確認手段の例 | 証明できること |
|---|---|---|
| 送信アプリケーションから配送基盤への投入 | 送信ログ、リクエスト記録、テストダブル | 投入時に付与した内部ヘッダー |
| 配送基盤から最終メールボックスまで | メールボックスの「原文を表示」、ダウンロードした原文 | 最終受信時に残っているヘッダー |

配送途中で削除され得る内部ヘッダーは、最終受信原文に存在しないことだけを根拠に、投入時にも存在しなかったと判定しない。

投入時の証拠を取得できない場合は、メール受信の成否と内部ヘッダーの確認結果を分ける。後者は保留とし、完了に必要なログまたはリクエスト記録を QA 文書へ明記する。
