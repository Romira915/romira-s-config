# Herdr マルチエージェント・オーケストレーション

オーケストレータは計画・割り当て・検証・統合を担当し、作業そのものはワーカーに任せる。ワーカー操作の具体的なコマンドは `herdr-workers` スキルに従う（このスキルの手順に入る前に読み込む）。

## 0. 前提確認

1. `test "${HERDR_ENV:-}" = 1`。失敗したら Herdr 外であることを伝えて止まる。
2. `herdr-workers` スキルを読み込む。
3. 使えるエージェント種別を確認する: `herdr agent`（kinds 一覧）と、各 CLI が PATH にあるか（`command -v claude codex gemini opencode`）。

## 1. 分担するか判断する

ワーカーを立てるとトークンと時間がかかり、文脈の受け渡しで情報が落ちる。次のどれかに当てはまるときだけ分担する。

- 互いに独立して並列に進められる作業が2つ以上ある
- 別モデルの独立した視点に価値がある（クロスレビュー、設計案の比較、原因仮説の検証）
- 長時間の作業を自分の文脈から切り離したい

数回のコマンドで終わる作業や、強く依存し合う逐次作業は自分でやる。

## 2. 計画を立ててユーザーに確認する

サブタスクごとに次を決め、表にしてユーザーに提示し、承認を得てから起動する（ワーカー数とモデルがコストを決めるため）。

| 項目 | 内容 |
|---|---|
| ワーカー名 | `[a-z][a-z0-9_-]{0,31}`、役割が分かる名前（例: `impl-api`, `review-gemini`） |
| kind / モデル | 割り当ての考え方は `references/patterns.md` |
| 担当範囲 | 触ってよいファイル・ディレクトリ。ワーカー間で重ならないようにする |
| 完了条件 | 何ができたら終わりか（テスト通過、レポート提出など） |
| 作業場所 | cwd。同じリポジトリを複数ワーカーが編集する場合は worktree が必要 |

- 同じ作業ツリーを複数ワーカーが同時に編集する計画にしない。編集範囲が重なる場合は、worktree を分けるか、逐次にする。
- worktree の作成（`herdr worktree create` / `git worktree add`）は、作業ツリーが clean でもユーザーの明示的な許可を得てから行う。
- ワーカー同士で直接やり取りさせない。情報の受け渡しは必ずオーケストレータを経由する。

## 3. 起動して指示する

1. run dir を作る（`herdr-workers` の「実行ディレクトリ」）。計画表を `$RUN_DIR/plan.md` に書き出す。
2. `herdr-workers` の `scripts/spawn-worker.sh` でワーカーを起動する。1体目は専用タブを作り、2体目以降は同じタブに並べる。
3. 各ワーカーへのプロンプトを `$RUN_DIR/<name>.prompt.md` に書き、`herdr agent prompt <name> "Read <path> and follow it."` のように渡す。並列実行時は `--wait` を付けずに全員へ投げる。

プロンプトに必ず入れるもの:

- 目的と背景（ワーカーは会話履歴を知らない）
- 担当範囲と、触ってはいけない範囲
- 完了条件と、検証に使うコマンド
- 禁止事項: commit / push / マージ、担当範囲外の編集、破壊的な git コマンド、外部サービスへの書き込み
- 報告形式: 変更したファイル、実行した検証とその結果、未解決の点

## 4. 監視する

- `herdr agent wait <name> --timeout <ms>` で各ワーカーを順に待つ。
- `blocked` になったら `herdr agent read` で内容を確認する。オーケストレータが答えられる質問（計画の範囲内の事実確認）は `agent prompt` で答える。権限の承認や方針の判断はユーザーに上げる。
- 進捗が見えない・同じ失敗を繰り返すワーカーは、`esc` で止めて指示を具体化するか、自分で引き取る。

## 5. 検証して統合する

- ワーカーの報告をそのまま採用しない。`git diff`、テスト出力、該当コードを自分で確認する。
- クロスレビューでは、指摘ごとに複数モデルの一致・不一致を整理し、根拠を一次情報で確かめてから採否を決める。多数決で決めない。
- 統合時に矛盾があれば、どちらの前提が正しいかを確認してから選ぶ。必要なら片方のワーカーに相手の結果を渡して反論させる。
- commit・push・PR 作成は、ユーザーの指示がある場合にオーケストレータが行う。

## 6. 報告と後片付け

1. ユーザーへの報告: ワーカーごとの担当・結果・検証状況（確認済み／未確認）、統合した成果、残課題。
2. `herdr-workers` の `scripts/cleanup-workers.sh --run-dir "$RUN_DIR"` で自分が作ったペイン・タブを閉じる。ユーザーが残したいワーカーは `--keep` で残す。
3. worktree を作った場合は、変更を統合済みかを確認し、削除してよいかユーザーに確認する。
