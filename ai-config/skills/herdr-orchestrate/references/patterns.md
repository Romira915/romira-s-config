# 分担パターンと割り当て

## kind・モデルの割り当て

- 使える kind は `herdr agent` の一覧と、PATH 上の CLI で決まる。モデルは各 CLI のフラグ（`<cli> --help` で確認）を `spawn-worker.sh ... -- <flags>` で渡す。
- ユーザーが kind・モデルを指定したら、それに従う。
- 指定がなければ、目的で選ぶ:
  - 独立した視点が欲しい（レビュー、案出し、原因仮説）: 異なるベンダーのモデルを混ぜる。同じモデルを複数立てても視点は似通う。
  - 定型的で範囲が明確な作業（機械的な置換、テスト追加、調べもの）: 軽量・低コストのモデルでよい。
  - 設計判断や広範囲の変更: 高性能なモデルを使うか、オーケストレータ自身が担う。
- 割り当てた理由を計画表に1行で書き、ユーザーが変更できるようにする。

## パターン1: 並列実装

独立した複数の変更を同時に進める。

1. 変更範囲がファイル単位で重ならないように分割する。重なる場合は worktree を分ける（ユーザーの許可が必要）か、逐次にする。
2. 各ワーカーに担当範囲・完了条件・検証コマンドを渡す。
3. 全員の完了後、オーケストレータが差分全体を確認し、全体のテストを実行する。

## パターン2: クロスレビュー

同じ差分を複数モデルに独立にレビューさせ、指摘を突き合わせる。

1. 各ワーカーに同じ対象・同じ観点を渡す。他のワーカーの存在や結果は最初は伝えない（引きずられないため）。
2. 指摘を「全員一致」「一部のみ」に分類する。一部のみの指摘も、根拠を確認して妥当なら採用する。
3. 判断が割れた指摘は、反対側のワーカーに相手の指摘と根拠を渡して再検討させ、最終判断はオーケストレータが一次情報で行う。
4. コードを書き換えるのは、ユーザーが修正を依頼した場合だけ。

## パターン3: 案出し比較

設計案・調査方針などを複数モデルに独立に出させて比較する。

1. 同じ要件・制約を渡し、案と根拠・トレードオフを求める。
2. オーケストレータが要件に照らして一つの推奨案に絞り、他案から取り入れる点を明示してユーザーに提示する。案を並べたまま判断を投げない。

## パターン4: 実装とレビューの分離

1. 実装ワーカーが変更を作る。
2. 別ベンダーのレビューワーカーに差分をレビューさせる。
3. オーケストレータが指摘の採否を決め、採用分だけ実装ワーカーに修正を指示する。往復は2〜3回までにし、収束しなければユーザーに判断を仰ぐ。
